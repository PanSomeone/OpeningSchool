# 开源许可与源码保护大纲

这不是法律意见。正式发布前，建议按下面的边界逐项确认，特别是从其他项目移植的代码和学校数据。

## 1. 推荐组合

| 部分 | 建议许可 | 原因 |
| --- | --- | --- |
| 应用主体（`app`、`core`、`feature`、内置插件） | **AGPL-3.0** | 强 copyleft，修改后分发 APK 或提供网络服务都必须继续开源；对“直接拿走闭源”的威慑最强 |
| 外部适配器协议、示例代码、文档 | **Apache-2.0** | 允许第三方写适配器而不必公开其适配器源码，利于生态 |
| 名称、Logo、应用图标、赞助二维码、截图 | **保留所有权利** | 商标与品牌不属于代码许可；fork 必须换名换图标 |
| 官方 release 签名密钥、插件签名校验、后端密钥 | **不公开** | 与源码许可无关；泄露会导致伪造更新或插件 |
| 未来的云端/付费服务 | **单独商业许可** | 不要放在公开仓库；采用 open-core 而不是假装全部开源 |

应用仓库根目录可以放 AGPL-3.0 的 `LICENSE`，再放一份 `NOTICE` 说明品牌与插件协议例外。不要让“开源”与“保留全部源码”同时成立；如果确实要保留核心源码，应明确采用 **source-available / open-core**，而不是 OSI 开源许可。

## 2. 为什么不建议只用 MIT / Apache-2.0

这两种许可允许他人把代码改进后闭源发布，甚至直接换皮上架。若目标是防止直接窃取，它们只能保留版权归属，不能阻止闭源分发。AGPL-3.0 也不能从技术上阻止复制，但它要求衍生作品继续开源，是当前最强的法律约束。

## 3. “防止被直接窃取”的可执行手段

1. **许可与版权**：AGPL-3.0 + 版权声明 + `NOTICE`；对闭源分发保留追责依据。
2. **品牌隔离**：名称“开源大学 / OpeningSchool”、Logo、图标不随代码授权；fork 必须使用不同名称和图标。
3. **发布签名**：release keystore 只保存在本地/密码管理器；任何官方更新必须使用同一签名。不要提交 `keystore.properties`、`.jks`、token。
4. **插件签名校验**：官方插件市场只信任用官方密钥签名的 APK；目录里记录 SHA-256，下载后先校验再安装。
5. **代码裁剪/混淆**：Release 已启用 R8（`isMinifyEnabled = true`）和资源压缩；保留必要的序列化/Jsoup 规则。混淆提高逆向成本，但不是安全边界。
6. **服务端资产**：把真正需要保护的逻辑放在自己的服务端（如果以后有），客户端只保留协议；不要把服务端密钥打进 APK。
7. **开源核心、闭源扩展**：公开适配器 API 与基础课表，插件市场的审核/签名/云端目录保持独立；这比“代码里藏一段”更可持续。

## 6. 建议的仓库结构

```text
LICENSE                 # AGPL-3.0（应用主体）
NOTICE                  # 品牌、来源、第三方署名
docs/LICENSE_POLICY.md  # 本大纲
core/plugin-api/        # Apache-2.0（可单独放 LICENSE）
market/catalog.json     # 插件条目 + sha256 + 许可
```

如果要保留一部分源代码不公开，建议把该部分拆成独立私有模块/服务，公开仓库不要包含其实现；不要在 AGPL 代码里放“禁止复制”的矛盾声明。
